# Pfennig: strategic review and open-work inventory

Reviewed 2026-10-08 against `652d205` (0.11.1). This is an advisory inventory, not an approved implementation roadmap. Priorities below are recommendations awaiting the owner's direction. Existing scope decisions remain in force.

## Assessment

Pfennig already has a coherent working product: document intake, a native ledger and inspector, persistent chat using the same agent, deterministic accounting, UStVA XML, EÜR CSV, and signed releases. Roughly 8,000 lines of production Swift implement the app and its two modules. The separation is sensible: the model interprets documents; Swift owns arithmetic, validation, persistence, authorization and exports. There is no evidence here that a rewrite or new architectural layer is needed.

The strongest next milestone is a complete, explainable quarter with tolerable review effort. Import accuracy alone is insufficient: omissions, duplicate transactions, payment assumptions and correctable exceptions determine whether the owner can depend on the resulting books.

The public-product ambition is less settled than the code. The landing draft promises a EUR 10/month managed AI subscription from 1.0, while the app requires the user's own API key. Treat that as a consequential product and operating-model decision, not an unfinished settings screen.

## Direction options

### Recommended: personal reliability, then a narrow public beta

Keep the existing target user and native ledger. Make the agent good at getting data in and resolving exceptions; keep review and deterministic exports central. The next milestone should use a complete quarter: import documents, account for relevant payments through the existing chat/manual workflow, review, reconcile totals against an independent reference, and inspect the export. Measure review minutes, material corrections, unexplained missing/extra transactions and repeatability. This uses the existing app and eval investment rather than requiring new architecture.

After that, a small cohort with similar bookkeeping can reveal which of today's manual exceptions actually recur. This is a recommendation, not a decision to recruit users or publish anything.

### Alternative: a small public utility with bring-your-own-key AI

Most of the distribution machinery already exists. The work shifts toward onboarding, understandable scope boundaries, archive recovery, stable updates and annual tax support. The API-key setup is a real audience constraint. This is a smaller operating commitment than selling model access, but still creates maintenance and support expectations.

### Separate decision: managed AI subscription

`landing-concepts/copy.md:126` promises EUR 10/month from 1.0; `landing-concepts/README.md` confirms this was intentional draft positioning. No equivalent subscription product is present in the reviewed app. Delivering it entails payment/entitlement handling, secure service access, usage economics, outage behavior and support. Define the audience and business case before implementing any of it. Preserve local bookkeeping and distinguish it clearly from remote document processing. Do not silently treat the draft as permission to add a backend.

## Proposed sequence and open decisions

1. Agree whether the immediate destination is dependable personal use, a narrow public utility, or a commercial service.
2. Reconcile the status/backlog and privacy description. Keep historical records, but make today's acceptance gaps explicit.
3. Investigate the duplicate-import and document-evidence cases with bounded synthetic experiments. Preserve the short prompt and agent-first design.
4. Complete one quarter with the existing UI, then test export additions and isolated archive recovery. Let observed friction determine any feature work.
5. Schedule 2027 verification as maintenance. Only then choose the next audience-facing feature or launch milestone.

The key question for the owner: what currently prevents using Pfennig as the normal bookkeeping workflow, and how much of that is trust versus missing capability? No implementation plans or external issue edits have been authorized by this inventory. Select the next bounded topic after that conversation.

## Considered and not recommended

- A rewrite, repository split, document-specific parser, new matching engine or broad performance refactor: no evidence that these are the next bottleneck. SQL writes scan bookings before/after and SELECT results are capped after materialization (`Sources/Core/SQLTool.swift:83`, `:87`, `:170`); measure realistic archive sizes before optimizing this deliberately small app.
- Adding an activity UI, undo framework or excluding unreviewed bookings from exports: those would reverse explicit owner decisions, not fix discovered defects.
- Treating chat's complete-history replay or default payment assumptions as accidental bugs: both are deliberate, documented tradeoffs. Evaluate their practical cost and correctness in the chosen workflow before revisiting them.
- Claiming ELSTER upload is entirely unverified: the September 14 upload is recorded as successful. Only subsequent additions remain explicitly outstanding.
- Claiming green offline tests establish agent accuracy, legal compliance or external acceptance: they establish none of those by themselves.
- Calling the pre-1.0 single-schema policy a defect: it is intentional. Wider distribution would need an explicit future data-preservation decision, not an unsolicited migration framework now.
